## 第1章 系统概述

### 1.1 什么是 New API

New API 是一个基于 Go 语言构建的 AI API 网关/代理系统。它将 58 种上游 AI 提供商（OpenAI、Claude、Gemini、Azure、AWS Bedrock、DeepSeek、智谱、通义千问、Moonshot 等）聚合为一个统一的 OpenAI 兼容接口，对外提供一致的 API 体验。系统内置用户管理、多级计费、速率限制、监控告警等功能，是一个完整的 AI API 商业化运营平台。

### 1.2 核心功能一览

| 功能模块 | 描述 |
|----------|------|
| **多提供商聚合** | 支持 58 种上游渠道类型，涵盖对话、图像、音频、视频、嵌入等全部 AI 能力 |
| **OpenAI 兼容接口** | 对外提供标准 `/v1/chat/completions`、`/v1/embeddings` 等端点，无缝替换 |
| **智能路由调度** | 多级优先级 + 权重随机 + 自动故障转移 + 失败重试，保障服务可用性 |
| **双模式计费引擎** | 传统倍率计费（Ratio）+ 动态表达式计费（Tiered Billing），覆盖所有定价场景 |
| **订阅制套餐** | 完整的订阅计划 → 订单 → 配额重置生命周期，支持 Stripe/EPay/Waffo 等支付网关 |
| **多级用户体系** | 分组管理 + Token 管控 + 模型访问限制 + 配额告警 |
| **渠道亲和性** | 基于请求特征的渠道绑定，特定用户/模型/路径固定路由到指定渠道 |
| **安全防护** | SSRF 防护、IP 黑白名单、敏感词过滤、速率限制、模型级请求频率控制 |
| **运营看板** | 请求量/消费统计、模型排行、渠道健康度、数据导出 |
| **多语言** | 后台 + 前台均支持中/英/法/俄/日/越多语言 |

### 1.3 支持的 AI 能力类型

| 能力类型 | 代表模型/服务 | API 端点 |
|----------|--------------|----------|
| **对话补全** | GPT-5, Claude 4, Gemini 2.5, DeepSeek-V3, Qwen3 | `/v1/chat/completions` |
| **文本补全** | GPT-3.5-turbo-instruct, Codex | `/v1/completions` |

## 第2章 快速开始

### 2.1 部署方式

New API 支持以下部署方式：

| 方式 | 适用场景 | 说明 |
|------|----------|------|
| **Docker Compose** | 推荐 | 一键部署，含数据库和 Redis |
| **Docker 单容器** | 测试/轻量 | 单容器运行，需外部数据库 |
| **二进制部署** | 自定义环境 | 直接运行编译好的可执行文件 |
| **Kubernetes** | 生产集群 | Helm Chart 部署 |

### 2.2 首次访问与初始化

1. 启动服务后，打开浏览器访问 `http://localhost:3000`（默认地址）
2. 首次运行时，系统处于未初始化状态，前端将自动引导进入**设置向导**
3. 按向导完成以下步骤：

**步骤一：创建根管理员账户**
- 设置管理员邮箱和密码（根用户角色为 `Root`，拥有最高权限）
- 这是系统的第一个账户，请妥善保管

**步骤二：数据库配置**
- **SQLite**（默认）：零配置，数据文件存储在本地，适合单机测试
- **MySQL**（≥ 5.7.8）：适合中等规模生产环境
- **PostgreSQL**（≥ 9.6）：适合大规模生产环境，JSON 支持更好

**步骤三：使用模式选择**
- **自用模式**（`SelfUseMode`）：隐藏用户管理界面，适合个人或小团队直接使用
- **运营模式**（默认）：完整的多用户管理功能，支持计费和订阅

> 💡 **提示**：初始化完成后，可在「系统设置 → 通用设置」中随时修改大部分配置。

### 2.3 登录系统

- 访问登录页，输入邮箱和密码
- 支持多种登录方式（需管理员在系统设置中启用）：

| 登录方式 | 配置复杂度 | 安全性 | 说明 |
|----------|-----------|--------|------|
| **邮箱+密码** | 低 | 中 | 默认方式，开箱即用 |
| **GitHub OAuth** | 低 | 中 | 申请 GitHub OAuth App 即可 |
| **Discord OAuth** | 低 | 中 | 需 Discord Developer Portal 配置 |
| **OIDC** | 中 | 高 | 通用 OIDC 协议，支持 Keycloak/Auth0 等 |
| **自定义 OAuth** | 中 | 高 | 支持任意 OAuth2.0 提供商，含访问控制策略 |
| **Passkeys/WebAuthn** | 低 | 高 | 生物识别登录，推荐开启 |

## 第4章 渠道管理（核心运营）

> **本章是运营工作最核心的章节。**渠道是连接上游 AI 服务商的桥梁，渠道配置的质量直接决定服务的可用性、成本和用户体验。

### 4.1 渠道概念模型

一个"渠道"代表一个上游 AI 服务商的**一组凭证和配置**。每条渠道的核心要素：

```
┌─────────────────────────────────────────────────────┐
│                      渠道 (Channel)                   │
├─────────────┬──────────┬──────────┬─────────────────┤
│  提供商类型  │  API 密钥  │  模型列表  │  优先级 + 权重   │
│  (58种可选)  │ (支持多KEY) │ (模型映射) │  (路由调度策略)   │
└─────────────┴──────────┴──────────┴─────────────────┘
```

例如：一个 OpenAI 付费账户可创建 1 条渠道（或 N 条渠道使用不同 Key），一个 Azure 资源对应 1 条渠道。

### 4.3 创建渠道（完整参数说明）

#### 4.3.1 基础信息

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| **名称** | 文本 | ✅ | 渠道的标识名称，如"OpenAI-Pro-01" |
| **渠道类型** | 下拉 | ✅ | 从 58 种类型中选择上游服务商 |
| **分组** | 多选 | ✅ | 将渠道分配给哪些用户分组（可多选，不选则全局可用） |
| **状态** | 开关 | - | 启用 / 禁用。禁用后该渠道不再接收请求 |

#### 4.3.2 认证配置

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| **API 密钥** | 密码 | ✅ | 上游服务商的 API Key。支持加密存储 |
| **Base URL** | URL | - | 自定义 API 端点地址（适用于代理、私有部署） |
| **额外请求头** | JSON | - | 向上游请求时附加的 HTTP 头，如 `{"X-Custom": "value"}` |
| **MCP Server** | JSON | - | MCP 服务配置（用于支持 MCP 协议的渠道） |
| **代理地址** | URL | - | 通过 HTTP/SOCKS5 代理连接上游 |

#### 4.3.3 模型配置

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| **模型列表** | 数组 | ✅ | 该渠道支持的模型名称列表。支持通配符 `*` |
| **自动同步模型** | 开关 | - | 开启后定时从上游拉取最新模型列表（OpenAI/Gemini 等支持 `/v1/models` 的渠道） |
| **模型映射** | JSON | - | `{"用户请求的模型名": "上游模型名"}`，详见 §4.8 |

#### 4.3.4 高级调度参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| **优先级** | 整数 | 0 | **数值越小越优先**。同一模型有多个渠道时，优先选择优先级高的渠道 |
| **权重** | 整数 | 0 | 加权随机选择的权重。为 0 时不参与加权。同一优先级内按权重比例分配流量 |
| **封禁阈值** | 整数 | 5 | 连续失败多少次后自动封禁（0 = 不自动封禁） |
| **请求超时** | 秒 | 300 | 单次向上游请求的超时时间 |
| **请求间隔** | 毫秒 | 0 | 同一 Key 连续两次请求之间的最小间隔（用于规避速率限制） |

### 4.4 渠道路由调度机制

系统收到一个 API 请求时的调度流程：

```
1. 用户请求 model: "gpt-4o"
         │
2. 查找该分组下所有支持 "gpt-4o" 的可用渠道
         │
3. 按 优先级 升序排列 → 同优先级内按 权重 随机选择
         │
4. 尝试请求选中的渠道
         │
    ┌────┴────┐
    │ 成功 ✅  │──→ 返回结果，更新渠道健康状态
    └─────────┘
    ┌────┴────┐
    │ 失败 ❌  │──→ 记录失败次数，触发自动封禁检查
    └─────────┘
         │
5. 根据 重试次数 配置，自动切换到下一个渠道重试
```

**优先级设计建议**：

| 场景 | 推荐配置 |
|------|----------|
| **主备架构** | 主渠道优先级=0，备用渠道优先级=10，自动故障转移 |
| **负载均衡** | 多个渠道同一优先级，不同权重，如 50:30:20 分流 |
| **成本优化** | 低成本渠道优先，高成本渠道做备份 |
| **地域分流** | 结合渠道亲和性（§11.4），将用户固定到最近的渠道 |

### 4.5 自动封禁与恢复

#### 4.5.1 触发条件

当渠道满足以下任一条件时，系统自动将其**封禁**（状态变更为禁用）：

| 触发条件 | 配置位置 | 说明 |
|----------|----------|------|
| **连续失败次数达阈值** | 渠道「封禁阈值」 | 连续 N 次请求失败 |
| **返回特定错误码** | 系统设置 → 自动封禁状态码 | 如上游返回 401（Key 无效）、402（余额不足） |
| **返回特定关键词** | 系统设置 → 自动封禁关键词 | 如 `"Your credit balance is too low"`、`"Permission denied"` 等 |

系统默认配置的自动封禁关键词包括：

- `"Your credit balance is too low"`
- `"You exceeded your current quota"`
- `"Permission denied"`
- `"insufficient_quota"`
- `"account is not active"`
- `"billing_not_active"`
- 等多条匹配规则

#### 4.5.2 自动恢复

可在系统设置中开启「自动启用被封渠道」：

- 封禁一段时间后，自动恢复为可用状态
- 管理员也可手动在渠道管理页面点击「解封」

> ⚠️ **运营建议**：定期检查被封禁的渠道列表。如果某个渠道频繁被封禁，说明上游 Key 可能已失效或余额不足，应及时更换。

### 4.6 多密钥模式

对于需要多个 API Key 轮询使用的场景（如规避速率限制、增加并发）：

1. 在渠道编辑页开启「多密钥模式」
2. 添加多个 API Key（每行一个，或 JSON 数组）
3. 系统在每次请求时**自动轮询**选择不同的 Key
4. 多 Key 共享该渠道的优先级、权重、模型列表等配置

### 4.7 渠道健康测试

#### 4.7.1 手动测试

1. 在渠道列表中找到目标渠道
2. 点击「测试」按钮
3. 系统发送一条轻量级测试请求（如 `/v1/models` 或简单对话）
4. 返回测试结果：成功/失败及错误详情

#### 4.7.2 自动测试

管理员可在「系统设置 → 监控设置」中配置：

| 参数 | 说明 |
|------|------|
| **启用自动测试** | 开启后系统定时对所有启用渠道发送测试请求 |
| **测试间隔** | 默认 10 分钟。支持环境变量 `CHANNEL_TEST_FREQUENCY` 覆盖 |

自动测试结果会通过配置的通知渠道（邮件/Bark/Gotify）发送给管理员。

### 4.8 模型映射（Model Mapping）

模型映射让你可以用**自定义名称**暴露模型给用户，或将多个上游模型合并到一个名称下：

#### 使用场景

| 场景 | 示例 |
|------|------|
| **隐藏真实模型名** | 用户用 `"fast-model"` → 上游实际用 `"gpt-4o"` |
| **多模型聚合** | 多个渠道的不同模型都映射为 `"gpt-4o"`，系统自动选择可用渠道 |
| **版本平滑升级** | `"gpt-4"` → `"gpt-4-0613"`，发布新版时只需修改映射 |

#### 配置方法

在渠道编辑页的「模型映射」中填入 JSON：

```json
{
  "gpt-4o": "gpt-4o-2024-08-06",
  "gpt-4-turbo": "gpt-4-turbo-2024-04-09",
  "claude-sonnet": "claude-3-5-sonnet-20241022"
}
```

**映射支持链式传递**：A → B → C，系统自动追踪到最终的模型名。同时内置**环路检测**，防止 A → B → A 的死循环。

### 4.9 渠道运营最佳实践

1. **主备冗余**：每个关键模型至少配置 2 条不同上游的渠道（如 OpenAI + Azure），互为备份
2. **优先级分层**：
   - 优先级 0-9：主力渠道（高质量、稳定）
   - 优先级 10-49：备用渠道（不同区域/账号）
   - 优先级 50-99：兜底渠道（OpenRouter 等聚合平台）
3. **定期巡检**：开启自动测试，每天检查一次封禁列表
4. **余额监控**：关注上游 Key 的余额/配额，提前续费
5. **模型映射统一管理**：使用模型映射抽象出统一的模型名称体系，降低用户迁移成本

## 第5章 模型管理（核心运营）

> 模型管理定义了"用户可以调用哪些模型"以及"这些模型如何计价"。它是连接渠道、定价和用户权限的中枢。

### 5.1 模型管理三要素

模型管理涉及三层配置，需协同工作：

```
┌─────────────────────────────────────────────────────────┐
│                    模型元数据 (Model Meta)                 │
│  模型名称 · 图标 · 标签 · 描述 · 厂商归属 · 端点类型          │
├─────────────────────────────────────────────────────────┤
│                    渠道能力 (Ability)                      │
│  模型 ←→ 渠道 ←→ 分组  的三方关联，含优先级和权重              │
├─────────────────────────────────────────────────────────┤
│                    定价配置 (Pricing)                      │
│  倍率/单价 · 完成倍率 · 缓存倍率 · 分组比例 · 分层表达式       │
└─────────────────────────────────────────────────────────┘
```

### 5.2 模型名称匹配规则（NameRule）

系统在查找模型配置时，支持四种名称匹配规则：

| 规则 | 常量值 | 说明 | 示例 |
|------|--------|------|------|
| **精确匹配** | `0` | 完全一致的名称 | `gpt-4o` 只匹配 `gpt-4o` |
| **前缀匹配** | `1` | 按前缀模糊匹配 | `gpt-4` 匹配 `gpt-4o`、`gpt-4-turbo`、`gpt-4-0613` |
| **包含匹配** | `2` | 名称包含关键字 | `claude` 匹配 `claude-3-opus`、`claude-3.5-sonnet` |
| **后缀匹配** | `3` | 按后缀模糊匹配 | `-turbo` 匹配 `gpt-4-turbo`、`gpt-3.5-turbo` |

> 💡 **运营技巧**：利用前缀匹配规则，可用一条配置覆盖整个模型系列。例如配置 `gpt-4` 为前缀匹配，所有 GPT-4 变体自动生效。

### 5.3 模型元数据管理

#### 5.3.1 模型字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| **模型名称** | 文本 | 唯一标识，如 `gpt-4o`。为精确匹配和前缀匹配的基础 |
| **描述** | 文本 | 模型简介，在前端展示给用户 |
| **图标** | URL/文本 | 模型图标 URL 或 CSS class |
| **标签** | 文本 | 用于分类检索，如 `"openai,chat,vision"` |
| **厂商** | 下拉 | 关联的厂商（Vendor），用于 `owned_by` 字段和前端分组展示 |
| **端点类型** | JSON | 支持的 API 端点类型，如 `{"openai": true, "anthropic": true}` |
| **名称规则** | 下拉 | 精确/前缀/包含/后缀匹配 |
| **状态** | 开关 | 启用/禁用。禁用后模型不再对外暴露 |
| **启用分组** | 多选 | 限制哪些用户分组可以访问此模型（空 = 全部分组可用） |
| **配额类型** | 选择 | 使用哪种配额：倍率配额 / 按次配额 |

#### 5.3.2 从上游同步模型

系统支持从官方元数据源同步最新的模型和厂商信息：

1. 进入「模型管理」→「同步上游模型」
2. 点击「预览」查看待新增/更新的模型列表
3. 确认后点击「同步」，系统自动创建/更新模型元数据和厂商信息

数据来源：`https://basellm.github.io/llm-metadata/api/newapi/models.json`，支持多语言（中/英/日）。

#### 5.3.3 发现缺失模型

当渠道中配置了某些模型，但模型元数据表中没有对应记录时：

1. 进入「模型管理」→「缺失模型」
2. 系统自动扫描 abilities 表与 models 表的差异
3. 批量创建缺失的模型元数据

### 5.4 渠道能力关联（Ability）

Ability 是模型、渠道、分组之间的三方关联表，每一行代表：

> **某个分组**的用户可以通过**某个渠道**调用**某个模型**，且该渠道在此模型上有特定的**优先级**和**权重**。

| 字段 | 说明 |
|------|------|
| **分组** | 用户分组名称，如 `default`、`vip` |
| **模型** | 模型名称，如 `gpt-4o` |
| **渠道 ID** | 关联的渠道 |
| **启用** | 该关联是否生效 |
| **优先级** | 在此模型+分组下的渠道优先级（覆盖渠道自身优先级） |
| **权重** | 在此模型+分组下的渠道权重 |
| **标签** | 自定义标签，用于渠道亲和性匹配 |

> 💡 当你创建一个渠道并添加模型时，系统会自动创建相应的 Ability 关联。你可以在渠道编辑页直接管理这些关联。

### 5.5 预填充分组（Prefill Group）

预填充分组是一组预定义的模型/标签/端点集合，可以快速应用到渠道或用户配置中：

| 类型 | 说明 | 示例 |
|------|------|------|
| **模型列表** | 一组模型名称 | `["gpt-4o", "gpt-4-turbo", "claude-3.5-sonnet"]` |
| **标签集合** | 一组标签 | `["openai", "chat"]` |
| **端点列表** | 一组 API 端点 | `["/v1/chat/completions", "/v1/embeddings"]` |

在配置渠道的模型列表或用户的模型限制时，可直接选择预填充分组而无需逐个输入。

### 5.6 厂商管理（Vendor）

厂商（Vendor）用于将模型按提供商/品牌分组，影响前端 `GET /v1/models` 接口中每个模型的 `owned_by` 字段。

系统内置了常用的厂商映射（如 `gpt*` → OpenAI、`claude*` → Anthropic），管理员可：
- 在「厂商管理」页面查看/编辑/新增厂商
- 设置厂商名称、描述和图标
- 系统也会在模型同步时自动创建未知厂商

## 第6章 API 密钥管理（核心运营）

> API 密钥是用户调用 API 的凭证。密钥的配置决定了用户**能用哪些模型**、**有多少配额**、**受限哪些规则**。

### 6.1 密钥（Token）数据模型

每个 API 密钥包含以下核心属性：

| 属性 | 类型 | 说明 |
|------|------|------|
| **名称** | 文本 | 密钥的标识名称，便于识别 |
| **密钥值** | 自动生成 | 形如 `sk-xxxxxxxx` 的唯一密钥字符串（创建后仅展示一次） |
| **所属用户** | 关联 | 绑定到哪个用户 |
| **所属分组** | 选择 | 该密钥使用哪个分组的定价和模型访问规则 |
| **状态** | 开关 | 启用 / 禁用 |
| **模型限制** | JSON | 限制可调用的模型白名单（空 = 不限制） |
| **请求限制** | 整数 | 请求频率限制（每分钟/每天） |
| **配额限制** | 整数 | 总可用配额（与用户配额独立） |
| **已用配额** | 只读 | 该密钥累计消耗的配额 |
| **过期时间** | 日期 | Unix 时间戳，过期后自动失效 |
| **允许 IP** | 文本 | 允许访问的 IP 地址列表（逗号分隔，支持 CIDR） |
| **备注** | 文本 | 管理员备注信息 |

### 6.2 创建密钥（完整步骤）

1. 进入「API 密钥」页面，点击「新建密钥」
2. 选择**所属用户**（密钥绑定到哪个账户）
3. 设置**密钥名称**（建议使用有意义的命名，如 `"张三-工作电脑"`）
4. 选择**所属分组**（决定计费比例和可用模型范围）
5. （可选）配置模型限制：
   - 留空 = 该分组下的全部模型可用
   - 填入模型名（逗号分隔）= 仅允许调用指定模型
6. （可选）设置过期时间
7. （可选）限制允许访问的 IP 地址
8. 点击「创建」，**立即复制密钥值**（关闭后无法再次查看）

> ⚠️ **安全提示**：密钥值仅在创建时展示一次。系统存储的是加密后的哈希值，原始密钥无法找回。如丢失，请删除旧密钥并创建新密钥。

### 6.3 用户配额体系

系统有两级配额控制：

#### 用户级别配额

| 字段 | 说明 |
|------|------|
| **配额总量** (`Quota`) | 用户账户的可用配额余额 |
| **已用配额** (`UsedQuota`) | 累计消耗的配额 |
| **请求次数** | 累计 API 调用次数 |

配额消耗公式（倍率模式）：

```
消耗配额 = modelRatio × completionRatio × groupRatio × tokenCount
```

其中：
- `modelRatio`：模型倍率（1 = $0.002/1K tokens）
- `completionRatio`：输出 token 的额外倍率（如 GPT-4o 输出价格是输入的 4 倍）
- `groupRatio`：用户分组倍率（VIP 可设置折扣倍率如 0.8）

#### 配额充值方式

| 方式 | 说明 |
|------|------|
| **管理员手动充值** | 在用户管理页直接修改配额（支持增加/减少/覆盖三种模式） |
| **在线支付充值** | Stripe / EPay / Waffo 支付网关，用户自助购买配额 |
| **订阅套餐** | 定期发放配额，详见第9章 |
| **签到奖励** | 每日签到赠送随机配额（需在系统设置中开启） |
| **邀请奖励** | 邀请新用户注册，双方获得配额奖励 |

### 6.4 Token 设置（系统级限制）

管理员可在「系统设置 → Token 设置」中配置：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| **每用户最大 Token 数** | 1000 | 单个用户最多创建多少个 API 密钥 |

### 6.5 API 调用方式

#### 支持两种认证头格式

```bash
# 方式一：Bearer Token（推荐）
curl -H "Authorization: Bearer sk-xxxxxxxxxxxxxxxxxxxxxxxx"

# 方式二：自定义头
curl -H "x-api-key: sk-xxxxxxxxxxxxxxxxxxxxxxxx"
```

#### 完整请求示例

```bash
# 非流式对话
curl -X POST http://your-domain.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer sk-xxx" \
  -d '{
    "model": "gpt-4o",
    "messages": [
      {"role": "system", "content": "你是一个有用的助手"},
      {"role": "user", "content": "介绍一下 New API"}
    ],
    "temperature": 0.7,
    "max_tokens": 2048
  }'

# 流式对话（SSE）
curl -X POST http://your-domain.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer sk-xxx" \
  -d '{
    "model": "gpt-4o",
    "messages": [{"role": "user", "content": "Hello"}],
    "stream": true
  }'
```

### 6.6 模型级请求频率限制

系统支持按用户维度对单个模型设置请求频率限制：

| 配置项 | 说明 |
|--------|------|
| **启用模型限频** | 是否开启模型级别的请求频率限制 |
| **限频窗口** | 时间窗口（分钟），默认 1 分钟 |
| **总请求限制** | 窗口内允许的总请求次数 |
| **成功请求限制** | 窗口内允许的成功请求次数（HTTP 状态 < 400） |
| **分组成员限频** | 不同分组可设置不同的限制值 |

> 💡 该功能配合渠道配置可实现精细的成本控制：例如限制每个用户每分钟调用 `gpt-4o` 不超过 20 次。

## 第7章 定价管理（核心运营）

> 定价是商业化运营的核心。New API 提供两套计费引擎和完整的分组折扣体系，覆盖从简单倍率到复杂阶梯定价的所有场景。

### 7.1 计费基础概念

#### 7.1.1 配额与货币的关系

系统内部使用"配额（Quota）"作为统一的计量单位：

```
1 QuotaPerUnit = 500,000 配额单位 = $0.002 USD / 1K tokens

即：500,000 配额 = $1.00 USD
```

前端可根据运营需要将配额显示为不同货币：

| 显示模式 | 换算关系 |
|----------|----------|
| **USD** | 500,000 配额 = $1.00 |
| **CNY** | 500,000 配额 = ¥7.30（按 USD/CNY=7.3） |
| **TOKENS** | 直接显示配额数值 |
| **自定义货币** | 通过系统设置配置汇率和货币符号 |

#### 7.1.2 两种配额类型

| 类型 | 常量 | 适用场景 | 扣费方式 |
|------|------|----------|----------|
| **倍率配额** (`QuotaType=0`) | Ratio-based | 对话、嵌入等按 Token 计费 | `modelRatio × completionRatio × groupRatio × tokens` |
| **按次配额** (`QuotaType=1`) | Price-based | MJ 绘图、DALL-E、视频生成 | `modelPrice × QuotaPerUnit × groupRatio`（每次固定） |

### 7.2 倍率计费体系（Ratio Mode）

#### 7.2.1 模型倍率（Model Ratio）

**核心公式**：`1 倍率单位 = $0.002 / 1K tokens`

| 模型 | 倍率 | 对应美元价格/1M tokens |
|------|------|----------------------|
| GPT-4o | 1.25 | $2.50 |
| GPT-4o-mini | 0.075 | $0.15 |
| Claude 3.5 Sonnet | 1.5 | $3.00 |
| DeepSeek-V3 | 0.14 | $0.28 |
| Gemini 2.5 Pro | 0.625 | $1.25 |

系统内置了 200+ 模型的默认倍率表。

#### 7.2.2 完成倍率（Completion Ratio）

输出 Token 通常比输入 Token 价格更高，通过完成倍率实现差异化：

| 模型 | 输入倍率 | 完成倍率 | 输出实际倍率 |
|------|----------|----------|-------------|
| GPT-4o | 1.25 | 4× | 5.0 |
| GPT-4-turbo | 7.5 | 3× | 22.5 |
| Claude 3.5 Sonnet | 1.5 | 5× | 7.5 |
| DeepSeek-V3 | 0.14 | 4× | 0.56 |

即：消耗配额 = `modelRatio × (inputTokens + completionRatio × outputTokens) × groupRatio`

#### 7.2.3 缓存倍率（Cache Ratio）

针对支持 Prompt Caching 的模型（Claude、Gemini、GPT-4.1 等）：

| 倍率类型 | 说明 | 典型值 |
|----------|------|--------|
| **缓存读取倍率** (`cache_ratio`) | 命中缓存时的折扣倍率 | Claude: 0.1, OpenAI: 0.5 |
| **缓存写入倍率** (`create_cache_ratio`) | 首次写入缓存的额外成本 | Claude: 1.25× |
| **1小时缓存写入倍率** | Claude 的 1h TTL 缓存 | 1.6× 基准 |

#### 7.2.4 图像/音频倍率

支持对多模态模型中的图像和音频 Token 单独定价：

| 倍率类型 | 说明 |
|----------|------|
| `image_ratio` | 图像输入 Token 的额外倍率 |
| `audio_ratio` | 音频输入 Token 的额外倍率 |
| `audio_completion_ratio` | 音频输出 Token 的额外倍率 |

#### 7.2.5 分组倍率（Group Ratio）

不同分组可设置不同的倍率系数，用于实现会员折扣：

```json
{
  "default": 1.0,
  "vip": 0.9,
  "svip": 0.8
}
```

VIP 用户消耗配额 = 标准配额 × 0.9（即 9 折）。

**分组间倍率**（Group-Group Ratio）：支持跨分组精细化定价：

```json
{
  "vip": {
    "default": 0.9,
    "premium": 0.85
  }
}
```

VIP 分组的用户使用 `default` 分组的模型时享受 0.9 倍率，使用 `premium` 分组的模型时享受 0.85 倍率。

#### 7.2.6 特殊分组规则

通过 `+` / `-` 前缀控制分组对模型分组的可见性：

- `+vip`：将 `vip` 分组追加到用户的可用模型分组列表
- `-default`：从用户的可用模型分组中移除 `default` 分组

### 7.3 按次计费（Price Mode）

适用于每次调用成本固定的场景（图像生成、视频生成、音乐生成等）：

| 服务 | 单价 | 计算方式 |
|------|------|----------|
| Midjourney Imagine | 0.2 | 每次生成固定 0.2 单价 |
| DALL-E 3 1024×1024 | 0.08 | `0.08 × QuotaPerUnit × groupRatio` |
| Suno 音乐生成 | 0.1 | 每首歌曲固定单价 |

系统内置了 100+ 按次计费模型的默认价格。

### 7.4 动态表达式计费（Tiered Billing）

> 表达式计费是最高阶的定价方式，支持按 Token 用量、时间段、请求参数等多维度动态计算费用。

#### 7.4.1 设计理念

**一个表达式 = 一个模型完整的计费逻辑。**无需额外配置缓存倍率、完成倍率——全部在表达式中定义。

表达式中的价格系数使用**真实美元价**（$/1M tokens），系统自动转换为内部配额。

#### 7.4.2 表达式变量

| 变量 | 含义 | 单位 |
|------|------|------|
| `p` | 纯文本输入 Token 数（自动排除缓存/图像/音频） | 个 |
| `c` | 纯文本输出 Token 数 | 个 |
| `len` | 输入上下文总长度（不回退排除，用于阶梯条件判断） | 个 |
| `cr` | 缓存命中（读取）Token 数 | 个 |
| `cc` | 缓存创建 Token 数（5 分钟 TTL） | 个 |
| `cc1h` | 缓存创建 Token 数（1 小时 TTL，仅 Claude） | 个 |
| `img` | 图像输入 Token 数 | 个 |
| `img_o` | 图像输出 Token 数 | 个 |
| `ai` | 音频输入 Token 数 | 个 |
| `ao` | 音频输出 Token 数 | 个 |

**变量智能排除**：如果表达式中使用了 `cr`（缓存读取），系统会自动从 `p` 中减去缓存命中的 Token 数，确保不重复计费。图像/音频变量同理。

#### 7.4.3 内置函数

| 函数 | 签名 | 说明 |
|------|------|------|
| `tier(name, value)` | `(string, float64) → float64` | 声明一个计费阶梯，返回费用，同时记录阶梯名用于日志 |
| `param(path)` | `(string) → any` | 读取请求体 JSON 中指定路径的值（通过 gjson） |
| `header(key)` | `(string) → string` | 读取请求头的值 |
| `has(source, substr)` | `(any, string) → bool` | 检查字符串/值是否包含子串 |
| `hour(tz)` | `(string) → int` | 当前小时（0-23），如 `hour("Asia/Shanghai")` |
| `weekday(tz)` | `(string) → int` | 当前星期几（0=周日），如 `weekday("UTC")` |
| `month(tz)` / `day(tz)` | `(string) → int` | 当前月份(1-12) / 日期(1-31) |
| `minute(tz)` | `(string) → int` | 当前分钟(0-59) |
| `max/min/abs/ceil/floor` | 标准数学 | 标准数学函数 |

#### 7.4.4 表达式示例

**示例 1：标准分层定价（Claude 风格）**
```
len <= 200000
  ? tier("standard", p * 3 + c * 15 + cr * 0.3 + cc * 3.75 + cc1h * 6)
  : tier("long_context", p * 6 + c * 22.5 + cr * 0.6 + cc * 7.5 + cc1h * 12)
```
- 200K tokens 以内：标准价格
- 超过 200K tokens：长上下文价格（2×）

**示例 2：高峰/低峰时段差异化**
```
tier("default", p * 2 + c * 10) * (hour("UTC") >= 21 || hour("UTC") < 6 ? 0.5 : 1)
```
- UTC 21:00-06:00（夜间低峰）：半价

**示例 3：请求特征感知**
```
tier("standard", p * 5 + c * 25) + (header("anthropic-beta") has "fast-mode" ? 6 : 0)
```
- 使用 fast-mode 时额外加收费用

#### 7.4.5 配置方式

1. 在「定价管理」页面，选择模型
2. 将计费模式切换为「动态表达式计费」（`tiered_expr`）
3. 输入表达式字符串
4. 保存时系统自动进行：
   - **语法编译校验**：确保表达式可以被正确解析
   - **烟雾测试**：用多组 Token 向量验证表达式能正常执行并返回非负数

### 7.5 定价同步（Ratio Sync）

支持从多个上游数据源同步定价信息：

| 数据源 | 说明 |
|--------|------|
| **其他 New API 实例** | 通过 `/api/pricing` 或 `/api/ratio_config` 端点拉取定价 |
| **OpenRouter** | 通过 `/v1/models` API 拉取 OpenRouter 的模型定价 |
| **models.dev** | 通过公开 API 拉取社区维护的模型成本数据 |

同步字段包括：`model_ratio`、`completion_ratio`、`cache_ratio`、`create_cache_ratio`、`image_ratio`、`audio_ratio`、`model_price`、`billing_mode`、`billing_expr`。

### 7.6 定价运营最佳实践

1. **分层定价策略**：
   - 默认分组：标准倍率（`group_ratio = 1.0`）
   - VIP：9 折（`group_ratio = 0.9`）
   - SVIP：8 折（`group_ratio = 0.8`）
2. **定期同步**：使用 Ratio Sync 功能从上游获取最新定价，确保成本覆盖
3. **表达式验证**：启用表达式计费前，先在测试环境充分验证
4. **倍率缓冲**：设置倍率时适当上浮 10-20%，预留上游涨价空间
5. **免费模型控制**：将 `groupRatio` 或 `modelRatio` 设为 0 即可实现免费调用

### 11.4 渠道亲和性（Channel Affinity）

渠道亲和性让你可以将特定特征的请求"粘"到固定的渠道上，实现精准路由：

#### 核心概念

| 配置项 | 说明 |
|--------|------|
| **启用** | 是否开启渠道亲和性 |
| **成功切换** | 成功请求后是否更新亲和记录（将后续请求也路由到此渠道） |
| **渠道禁用保持** | 亲和渠道被禁用后是否继续保留记录 |
| **最大记录数** | 亲和性表的最大条目数（默认 100,000） |
| **默认 TTL** | 亲和记录的过期时间（默认 3600 秒 = 1 小时） |

#### 规则配置

每条规则包含：

| 参数 | 说明 |
|------|------|
| **规则名称** | 用于标识 |
| **模型正则** | 匹配模型名称的正则表达式 |
| **路径正则** | 匹配 API 路径的正则表达式 |
| **键来源** | 从何处提取亲和键：上下文整数 / 上下文字符串 / 请求头 / GJSON 路径 |
| **键正则** | 对提取的键值进行正则匹配 |
| **TTL** | 该规则的亲和保持时间 |
| **参数覆写模板** | 匹配后修改请求参数的模板 |
| **失败跳过重试** | 亲和渠道失败时是否跳过重试（直接返回错误而非尝试其他渠道） |

#### 典型应用场景

- **GitHub Copilot 分流**：将 Copilot 请求固定到专用渠道
- **付费用户优先**：VIP 用户的请求优先分配到高质量渠道
- **地域就近路由**：根据请求来源 IP 地区选择最近的渠道

## 附录B 常见问题与故障排除

### B.1 渠道相关

**Q: 为什么创建了渠道但用户无法使用某个模型？**

检查清单：
1. 渠道的「模型列表」中是否包含该模型名称（注意大小写和前缀匹配规则）
2. 渠道的「分组」设置是否包含该用户所属的分组
3. 渠道状态是否为「启用」
4. 模型元数据（模型管理页）是否已配置且状态为启用
5. 模型是否被该用户的「模型限制」排除

**Q: 渠道一直被封禁，怎么排查？**

1. 查看日志中该渠道的失败原因（错误码、错误消息）
2. 检查 API Key 是否还有余额/配额
3. 检查上游服务是否正常（手动 curl 测试）
4. 检查网络连通性（是否需要代理）
5. 调整「自动封禁关键词」列表，排除误判

**Q: 如何做多渠道负载均衡？**

将多个渠道设置为相同优先级、不同权重。例如 3 个渠道权重分别为 50:30:20，系统会按比例随机分配请求。

### B.2 定价相关

**Q: 用户实际被扣了多少配额是怎么计算的？**

倍率模式：`消耗 = modelRatio × (inputTokens + completionRatio × outputTokens) × groupRatio`

例如：用户（vip 分组，groupRatio=0.9）调用 GPT-4o（modelRatio=1.25, completionRatio=4），消耗 1000 输入 + 500 输出 Token：
- 消耗 = 1.25 × (1000 + 4×500) × 0.9 = 1.25 × 3000 × 0.9 = 3375 配额

**Q: 如何设置某个模型免费？**

将模型的 `modelRatio` 或 `modelPrice` 设为 0，且不开启「免费模型预扣费」，该模型即免费用。

**Q: 表达式计费报错怎么办？**

1. 确认表达式语法正确（在表达式编辑器中会自动校验）
2. 确认使用的变量名在支持列表中
3. 确认 `tier()` 函数调用正确
4. 查看系统日志中的具体错误信息

### B.3 系统运维

**Q: 如何进行多机部署？**

1. 确保所有实例使用相同的数据库（MySQL/PostgreSQL）
2. 配置共享 Redis
3. 所有实例设置相同的 `SESSION_SECRET` 和 `CRYPTO_SECRET`
4. 定时任务（订阅重置）仅主节点执行

**Q: 如何备份数据？**

1. 数据库：使用数据库自带的备份工具（mysqldump/pg_dump 或直接复制 SQLite 文件）
2. 配置文件：备份环境变量和 `options` 表
3. 建议每日自动备份

**Q: 支持哪些数据库？**

| 数据库 | 最低版本 | 适用场景 |
|--------|----------|----------|
| SQLite | - | 单机测试、个人使用 |
| MySQL | 5.7.8 | 中等规模生产 |
| PostgreSQL | 9.6 | 大规模生产、JSON 操作频繁 |

**Q: 如何启用 Redis？**

设置环境变量：`REDIS_CONN_STRING=redis://localhost:6379/0`

Redis 用于：速率限制、缓存、会话管理、定时任务锁。

### B.4 安全相关

**Q: API 密钥泄露了怎么办？**

在「API 密钥」页面立即禁用或删除该密钥，创建新密钥替换。密钥原始值无法找回，只能重新生成。

**Q: 如何限制用户只能从特定 IP 访问？**

在创建/编辑 API 密钥时，在「允许 IP」字段中填入允许的 IP 地址（支持 CIDR 格式，如 `192.168.1.0/24`）。

**Q: 如何防止 SSRF 攻击？**

系统默认开启 SSRF 防护（`FetchSetting.EnableSSRFProtection = true`），阻止服务端请求访问内网地址。可在「系统设置 → 安全设置」中调整黑白名单。
